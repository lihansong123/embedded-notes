## 2026-10-27 · Keil armcc 报 `missing closing quote`（中文注释惹的祸）

**现象**
含中文注释的 `.c` 文件在 Keil 里编译报错：
```
error: #8: missing closing quote
error: #274: improperly terminated macro invocation
```
报错行看起来完全正常，引号也是配对的。

**定位**
做了三组对照实验，只改编码：

| 文件编码 | armcc 结果 |
|---|---|
| UTF-8 无 BOM | ❌ 4 errors |
| UTF-8 **with BOM** | ✅ 0 errors |
| GBK / ANSI | ✅ 0 errors |

**原因**
armcc（AC5）在中文 Windows 下默认按 **GBK** 解释源码。UTF-8 的中文是 3 字节，按 GBK 两两配对后，某些中文的"尾字节"正好落在 `"`（0x22）上，**把收尾引号当成了汉字的第二个字节吃掉** → 字符串没结束 → 宏调用没结束 → 报"引号缺失/宏未终止"。

**解决**
含中文的 `.c/.h` 一律存 **UTF-8 with BOM**（VSCode 右下角编码 → Save with Encoding → UTF-8 with BOM）。
BOM 等于告诉编译器"这是 UTF-8"，它就不会走 GBK 分支。

**一句话结论**
**报错在语法，病根在编码。** 中文注释 + Keil + 无 BOM = 定时炸弹，第一次遇到会怀疑人生。

## 2026-10-27 · PowerShell 5.1 报"缺少右 '}'"（同一个病根）

**现象**
一个语法完全正确的 `.ps1`，PowerShell 5.1 报：
```
语句块或类型定义中缺少右"}"。
```
`$PSVersionTable.PSVersion` = **5.1（Desktop）**，不是 PowerShell 7。

**原因**
和上面同源：Windows PowerShell **5.1** 读无 BOM 的 UTF-8 脚本时按 ANSI（GBK）解码，中文乱码后把引号/花括号搅乱。
（PowerShell 7 默认 UTF-8，同样的文件不会报错——所以"我这儿能跑"不代表用户那儿能跑。）

**解决**
`.ps1` 也存 **UTF-8 with BOM**。加 BOM 后解析器立刻通过（421 tokens，0 error）。

**一句话结论**
**给 Windows 写脚本/源码，UTF-8 with BOM 是最省事的默认值。** 跨环境的"编码假设"是最隐蔽的 bug 来源之一。

## 2026-10-27 · github.com 打不开，但 api.github.com 正常

**现象**
- 浏览器打不开 github.com（超时）
- `git clone/push` 也超时
- 但 `api.github.com` 返回 200

**定位过程（可复用的排查套路）**
1. `curl -o NUL -w "%{http_code} %{time_total}"` 测域名 → `000`（超时）
2. `Resolve-DnsName github.com` → 拿到 `20.205.243.166`（新加坡机房）
3. **裸 IP 直连**（`--resolve`）→ 也是 `000` ⇒ **不是 DNS 污染，是这个 IP 被阻断**
4. 拿 GitHub 各机房 IP 逐个试（`--resolve`）+ TCP 握手 + TLS 证书校验：
   - `20.205.243.166` ❌ TCP 不通
   - `20.27.177.113` ✅ **84ms**，`302`，证书校验通过
5. 结论：改 DNS 指向即可

**解决**
`hosts` 里加一行（需管理员）：
```
20.27.177.113 github.com
```
然后 `ipconfig /flushdns`。浏览器和 git 同时恢复。

**一句话结论**
"网站打不开"要分层排查：**DNS 解析 → TCP 握手 → TLS → HTTP**。逐层排除，别一上来就怀疑"被墙了"。
`api.github.com` 通而 `github.com` 不通，恰恰说明问题在**特定 IP 的链路**，不在域名本身。

> 备用 IP（按实测延迟）：`20.27.177.113` 84ms → `20.233.83.145` 143ms → `20.200.245.247` 184ms → `140.82.113.3` 245ms
